## Pré-condições e transporte

1. Obter autorização para a janela de QA e o SHA integral aprovado. Não usar a
   ponta de `main` implicitamente nem depender de uma branch móvel.
2. Confirmar no servidor autorizado: `hostname` deve corresponder a
   `uqphorders24-dev`; repo bare `/opt/zeroops/repo.git`, aplicação exportada
   `/opt/zeroops/src`, ambiente privado `/etc/zeroops/zeroops.env`.
   Inspecionar referências/hooks, versão atual e saúde antes de mudar algo.
   `src` vem de `git archive` e pode não conter `.git`; a versão publicada fica
   em `deploy/qa/VERSION` e `/api/health`.
3. Preservar configurações privadas, volumes e dados. Confirmar espaço para
   build e backup, checksum e leitura do backup anterior. Credenciais entram
   apenas por canais/ficheiros privados já instalados, nunca chat ou argumentos.
4. O remoto local `qa` tem post-receive com deploy. **Não fazer push de teste
   para esse remoto.** Para disponibilizar o commit, o operador pode fazer fetch
   explícito no bare QA (fetch não executa post-receive), por exemplo:

```bash
# Apenas numa futura janela autorizada, no servidor QA já confirmado.
REPO=/opt/zeroops/repo.git
SHA=<sha-integral-aprovado>
BRANCH=feat/p00-p01-project-permissions
git --git-dir="$REPO" rev-parse --is-bare-repository
git --git-dir="$REPO" fetch --no-tags https://github.com/nunomoreira1993/zeroops.git \
  "refs/heads/$BRANCH:refs/heads/staging/p00-p01"
test "$(git --git-dir="$REPO" rev-parse refs/heads/staging/p00-p01)" = "$SHA"
git --git-dir="$REPO" show --stat --oneline "$SHA"
```

Se o push da entrega estiver bloqueado, disponibilizar primeiro a branch num
destino privado verificado, ou transferir um bundle Git por canal autorizado.
Não substituir esse bloqueio por push no remoto de deploy. Rever divergências:
as histórias locais/GitHub podem ser distintas; não fazer merge/reset do QA.

Para o bundle verificado entregue localmente, transferi-lo apenas numa futura
janela autorizada, confirmar o SHA-256 comunicado e usar uma referência de staging:

```bash
BUNDLE=/caminho/privado/zeroops-p00-p01.bundle
sha256sum "$BUNDLE"
git --git-dir="$REPO" bundle verify "$BUNDLE"
git --git-dir="$REPO" fetch --no-tags "$BUNDLE" \
  "refs/heads/$BRANCH:refs/heads/staging/p00-p01"
test "$(git --git-dir="$REPO" rev-parse refs/heads/staging/p00-p01)" = "$SHA"
```

O fetch de bundle também não executa post-receive. Não mover `main` nem executar
deploy até à autorização explícita. O bundle é transporte de código, não backup
da BD/configuração nem prova de publicação GitHub.

## Smoke funcional obrigatório

Num projeto sintético QA, com contas admin, delegado, terceiro e membro de outro projeto:

1. Admin atribui gestão + edição ao delegado; delegado mantém o papel original.
2. Delegado abre “Permissões do projeto” sem acesso a contas/integrações.
   Atribui edição a terceiro; não concede gestão, ativação que não possui,
   papéis/flags administrativas, grants próprios ou de administradores.
3. Confirmar auditoria com ator/destinatário/projeto e grants antes/depois.
4. Com a mesma sessão, revogar edição ao delegado: gravação/autoria/aplicação
   seguintes são recusadas; grants já atribuídos ao terceiro permanecem.
5. Duas gravações com a mesma revisão: uma ganha, a outra recebe 409/reload;
   não perder alterações nem duplicar auditoria.
6. Editor sem ativação: editar draft/metadata é possível; publicar, mudar
   routing, associar alertas ou criar fluxo próprio de alerta é recusado.
   Leitor delegado de projeto vazio não cria/publica modelos ou perfis.
7. Testar separadamente simulação, ativação e gestão de perfis; nenhuma implica
   edição/administração. Um gestor de perfis sem edição não altera a etapa.
8. Repetir com IDs de outro projeto, membership desativada e projeto arquivado.
   Confirmar 403/404/409 adequados e ausência de efeitos colaterais.
9. Pedir autoria, revogar antes do claim e antes de aceitar: erro explícito e
   draft inalterado. Execuções já publicadas e decisões V1 continuam funcionais.
10. Desktop/mobile, menus, mensagens de erro, cookies/CSRF, ausência de erros JS.
    Autenticação real do Copilot por projeto deve ser testada separadamente dos fakes.

## Recuperação

- Build falhada antes da troca: o script mantém a versão anterior.
- Falha de migration/arranque/health: o script tenta repor código/imagens e
  identifica o backup. Validar efetivamente o SHA anterior e saúde; não assumir sucesso.
- A BD **não é restaurada automaticamente**. A migration 034 é aditiva e pode
  permanecer ao reverter código; não fazer DROP para “rollback”.
- Restaurar BD só com autorização específica e backup verificado, aceitando
  explicitamente perda de dados posteriores. Preservar auditoria/grants antes.
- Guardar SHA anterior, backup e resultados de smoke antes de promover QA a validado.
